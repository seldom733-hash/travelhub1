# Единый каталог фотографий отелей — итоговый отчёт

**Задача:** одна фотография на **физическую гостиницу**, общая для каталога отелей,
туров, всех поставщиков, глобального поиска и конструктора туров.

**Каталог файлов:** `frontend/public/hotels/` (public, gitignored)
**Публичный URL:** `/hotels/hotel_<hotelId>.webp` (никогда — абсолютный путь ОС)

---

## 1. Модель данных: что уже было и что добавлено

Аудит (Этап A) показал, что **сущности «отель» в проекте не было**:

| Что искали | Что нашли |
|---|---|
| `catalog."Hotel"` | не существовало |
| Отель как продукт | `Product.type = 'HOTEL'` (2857) — карточка-услуга, не гостиница |
| Тур | `Product.type = 'TOUR'` (5478) |
| `catalog."ProductMedia"` | S3-медиа **продукта**, 0 строк у supplier-синков → фото отеля там нет |
| `catalog."HotelCategory"` / `RoomType` / … | классификационные справочники, не отель |
| `geo."SupplierGeoLink"` (kind=HOTEL) | существующий словарь отелей поставщиков, 22 999 строк (использован для дозаполнения города, не как канон) |

Почему карточек/фото было много на один отель: имя файла строилось из **продукта**, а не из
гостиницы — тур писал `<tourinc>-<hotelKey>.jpg`, услуга «Отели» писала `htl-<hotelKey>.jpg`.
Один и тот же отель (тот же `hotelKey`) получал два файла, а разные туры с тем же отелем —
новые файлы.

Поэтому добавлены **две** таблицы (аддитивная миграция, без параллельной системы медиа):

- `catalog."Hotel"` — физическая гостиница (каноническая запись + ссылка на единственное фото);
- `catalog."HotelSupplierRef"` — привязка `(supplierCode, externalKey)` поставщика к гостинице
  (`@@unique([supplierCode, externalKey])`);
- enum `HotelPhotoStatus { NONE, PENDING, OK, FAILED, REVIEW }`.

В `Hotel` хранится только **ссылка на один файл** и его метаданные (`photoFile`,
`photoStatus`, `photoSource`, `photoSourceUrl`, `photoWidth/Height/Bytes`, `photoUpdatedAt`).
Никаких копий на тур/поставщика/оффер.

Миграция: `backend/prisma/migrations/20261015120000_add_hotel_photo_catalog/migration.sql`
применена через `prisma migrate deploy` (НЕ `migrate dev` — в БД есть известный дрейф,
`migrate dev` вызвал бы reset). Данные не удалялись, цены/наценки/комиссии/поставщики/логика
бронирования не затрагивались.

## 2. Сопоставление (Этап B): физические гостиницы

Канонический ключ — **нормализованное имя + страна + город**. Два уровня идентичности:

1. **supplier-native id** `(supplierCode, hotelKey)` — внутри поставщика. Один и тот же
   `hotelKey` в туре и в услуге «Отели» = одна гостиница (проверено: пересечение 1319).
2. **физическая гостиница** — `(normalizedName, countryCode, cityKey)`.

Звёздность в ключ **сознательно не входит**: поставщики переклассифицируют один отель
(`Dosso Dossi` 4★→5★, `Jaz Fanara` 4★→5★) — разделение создало бы два фото на одну гостиницу.
Такие случаи выведены в отчёт на ручную проверку.

Результат (`backend/scripts/hotel-registry.ts`, повторный запуск идемпотентен):

| Показатель | Значение |
|---|---|
| внешних id поставщиков (refs) | **5 331** |
| физических гостиниц (записей `Hotel`) | **4 878** |
| объединено между поставщиками | 7 |
| объединено внутри поставщика | 411 |
| конфликтов звёздности (в отчёт) | 33 |
| refs без имени | 0 |

Автоматически объединяется только подтверждённое совпадение; всё неоднозначное — в
`backend/data/hotels/hotel-ambiguous.json` (33 группы), авто-мердж по одному имени запрещён
и покрыт тестом.

## 3. Загрузка фотографий (Этап C)

`backend/scripts/hotel-photo-catalog.ts`

- Источник: Tripadvisor CDN. Прямые CDN-URL ищутся через **DuckDuckGo Images**
  (HTML `duckduckgo.com` → `vqd`-токен → JSON `i.js` с прямыми ссылками). Bing Images
  больше не подходит: его страница результатов стала JS-only и перестала отдавать
  `murl` в HTML (оставлен как резерв). HTML Tripadvisor закрыт DataDome, CDN картинок
  открыт. Результат принимается только если ВСЕ значимые слова названия отеля есть в
  заголовке/URL — иначе оставляем фолбэк, чтобы не подставить чужое фото.
- Обработка: `sharp` → WebP (ширина 1200, q 82, EXIF-поворот).
- Валидация: `failOn: error`, размер ≥ 5 КБ, стороны ≥ 400×300.
- Имя файла: **`hotel_<hotelId>.webp`** — стабильное, безопасное, детерминированное (один отель → один файл).
- Запись атомарная: `tmp` → `rename` (обрыв не оставит половинчатый файл).
- Идемпотентность: `photoStatus=OK` пропускается (кроме `--force`); повторный запуск не создаёт дубликатов.
- Журнал: `backend/data/hotels/photo-journal.jsonl` (источник, размеры, результат по каждому отелю).
- Опции: `--limit=N`, `--only=<id|name>`, `--ids-file=<path>` (построчный список id — точечный прогон по конкретным карточкам), `--status=A,B`, `--force`, `--dry-run`, `--width`, `--quality`, `--concurrency=N`, `--report`.
- Переиспользование: если у гостиницы с тем же (нормализованное имя, страна) фото уже есть —
  файл переиспользуется (`result: "reused"`), без повторной загрузки и без копии файла.

**Итог загрузки:** сохранено **4 603** файла из 4 878 гостиниц (см. §6).

## 4. Интеграция (Этап D): одна ссылка везде

Единая точка резолва — бэкенд отдаёт `hotelImage` в контракте витрины:

| Слой | Файл | Что сделано |
|---|---|---|
| Backend list/detail | `public-catalog.service.ts` | `hotelPhotoMap` (один запрос на выдачу) + `hotelImageForOne`; берут `photoFile` из реестра по `(supplierCode, hotelKey)`; legacy-файл по slug — только fallback |
| Backend DTO | `public-catalog.types.ts` | `hotelImage` в `PublicProductCard` и `PublicProductDetail.product` |
| Подсказки поиска | `public-suggest.service.ts` | `imageUrl` = фото из реестра (join на `HotelSupplierRef`/`Hotel`) |
| Инвалидация кэша | `hotel-photo-url.ts` | `hotelPhotoUrl(file, updatedAt)` → `/hotels/hotel_x.webp?v=<version>`: при замене фото ссылка меняется |
| Фронтенд (один хук) | `frontend/lib/hotel-photo.ts` | `useHotelPhoto(imageUrl, legacySlug)`; HEAD-проба с кэшем, включая промах |
| Карточки каталога/поиска | `ProductCard.tsx` | фото отеля, если нет `primaryImage` |
| Услуга «Отели» | `marketplace/Hotels.tsx` | **раньше вообще не показывала фото** — теперь как туры (паритет) |
| Туры | `Tours.tsx`, `HotTours.tsx`, `SpecialOffers.tsx`, `LatestOffers.tsx` | новый вызов хука |
| PDP | `products/[slug]/page.tsx` → `MediaGallery.tsx` | `hotelImage` прокинут в галерею |
| Витрина бизнеса | `storefront/StorefrontSite.tsx` | фото отеля в карточке |
| Глобальный поиск | `marketplace/GlobalSearchAutocomplete.tsx` | превью фото в подсказках |
| Раздача файлов | `app/hotels/[file]/route.ts` | добавлен `image/webp`, 404 с `cache-control` |

Туры без конкретного отеля сохраняют прежний механизм (фото тура/плейсхолдер).
Конструктор туров (`components/constructor/*`, `partner/TourConstructor.tsx`) изображений не
показывает вовсе — работает без изменений.

## 7. Перезапуск

```powershell
# 1. Реестр гостиниц (идемпотентно; пересобирает catalog."Hotel" + отчёты)
cd backend; npx tsx scripts/hotel-registry.ts

# 2. Фото: сначала пилот/сводка, потом полный прогон
npx tsx scripts/hotel-photo-catalog.ts --report          # сколько без фото
npx tsx scripts/hotel-photo-catalog.ts --dry-run --limit=10
npx tsx scripts/hotel-photo-catalog.ts --limit=100000    # докачает только отсутствующие

# 2a. Только один поставщик (склейка записей с разным написанием города + переиспользование фото)
npx tsx scripts/hotel-registry.ts --supplier=KAZUNION --merge-name-only

# 2b. Точечно по списку id (один id на строку) — например, только гостиницы за карточками без фото
npx tsx scripts/hotel-photo-catalog.ts --ids-file=data/hotels/photo-targets.txt --limit=100000

# 3. Повторить только неудачные (например, после сетевых сбоев)
npx tsx scripts/hotel-photo-catalog.ts --status=FAILED --limit=100000

# 4. Если сайт должен оставаться отзывчивым — снизить нагрузку
npx tsx scripts/hotel-photo-catalog.ts --limit=100000 --concurrency=1
```

Загрузчик перезапускаемый: уже сохранённые файлы и гостиницы со статусом `OK`
пропускаются, повторный прогон не создаёт дубликатов и не перезаписывает чужие фото
(перезапись — только с `--force`).

## 8. Права на изображения — требует подтверждения

Все загруженные фотографии получены из **Tripadvisor CDN** (пользовательский контент).
Массовая выкачка и публикация таких фото на коммерческом сайте ограничена ToS Tripadvisor и
авторским правом. Владелец проекта **принял ответственность** за такое использование
(явный выбор в диалоге) — на этом основании прогон выполнен.

Для каждого фото в `backend/data/hotels/photo-journal.jsonl` и в `Hotel.photoSourceUrl`
сохранён исходный URL — это позволяет позже:
- заменить источник на лицензируемый (официальные фото отелей / фиды поставщиков);
- указать атрибуцию;
- точечно удалить фото по требованию правообладателя.

**Список фото, которым нужен подтверждённый источник: 4 603 записи** — все с
`Hotel.photoSource = 'tripadvisor'` (100 % загруженных). Для каждой сохранён URL исходника
(`Hotel.photoSourceUrl`) и строка в журнале, поэтому источник можно заменить, добавить
атрибуцию или точечно удалить конкретное фото.

Отели без фото (275, см. §6 и `backend/data/hotels/hotels-without-photo.txt`) отображаются с
иконкой-фолбэком — их можно наполнить из официальных источников без изменений в коде
(достаточно положить файл `hotel_<hotelId>.webp` и заполнить `photoFile`/`photoStatus`).
