# PROMPT — UNIVERSAL TOUR SEARCH / SUMMER + КОМПАС

## 1. Цель

Реализовать в TravelHUB универсальный поисковик туров, который позволяет пользователю сформировать запрос по географии, датам, продолжительности и составу туристов, после чего получает **живые предложения и актуальные цены от поставщиков Summer и Компас**.

Поиск не должен работать как статический каталог. Результаты должны формироваться на основании фактической доступности и текущих цен поставщиков в момент поиска.

Главный сценарий:

**Параметры поиска → Summer + Компас → нормализация → объединение → таблица туров → карточка предложения → оформление заказа.**

---

## 2. Форма поиска

Создать единый блок поиска туров.

### Направление

Поля:

- Страна
- Город
- Курорт

Использовать **единый справочник География TravelHUB**.

Иерархия:

```text
Страна
 └── Город
      └── Курорт
```

Логика:

- страна ограничивает города;
- город ограничивает курорты;
- разрешён поиск только по стране;
- разрешён поиск страна + город;
- разрешён поиск страна + город + курорт;
- географическая единица показывается в поиске туров только при наличии актуальных активных предложений по категории «Туры».

Не создавать отдельные дублирующие справочники географии для Summer и Компас.

### Дата

Добавить выбор даты заезда.

Поддержать конкретную дату и, если это позволяет существующая архитектура, период поиска.

Если поставщик возвращает несколько дат заезда, каждая дата отображается отдельным результатом.

### Количество ночей

Добавить поле **Ночей**.

Поддержать конкретное количество ночей и диапазон, если это уже предусмотрено архитектурой.

### Туристы

Добавить selector:

```text
Взрослые
Дети
Возраст каждого ребёнка
```

Пример:

```text
2 взрослых
1 ребёнок — 7 лет
```

Возраст детей передавать поставщику, если он влияет на цену или доступность.

## 3. Кнопка поиска

Основная CTA:

**Найти туры**

После нажатия:

1. валидировать параметры;
2. сформировать единый внутренний SearchRequest;
3. параллельно запросить Summer и Компас;
4. получить ответы;
5. нормализовать их в модель TravelHUB;
6. объединить результаты;
7. обработать дубли;
8. применить сортировку/фильтрацию;
9. вывести таблицу.

Ошибка одного поставщика не должна блокировать результаты другого.

---

## 4. Живые цены

Цена должна приходить из текущего ответа поставщика.

Не использовать сохранённую старую цену как актуальную цену предложения.

Для результата хранить минимум:

```text
supplier
supplierOfferId
price
currency
availability
searchTimestamp
```

Перед бронированием предусмотреть повторную проверку актуальности, если она поддерживается API поставщика.

## 9. Booking flow

Использовать существующие сущности и сервисы TravelHUB:

```text

Order

```

Предпочтительный поток:

```text

      ↓
Offer Details
      ↓
Revalidate / Confirm
      ↓

      ↓
Booking
```

Если цена изменилась:

```text
Цена предложения изменилась.

Было: 890 AZN
Стало: 925 AZN
```

Запросить подтверждение пользователя.

Если предложение исчезло:

```text
Предложение больше недоступно.
```

Не создавать заказ по устаревшему или недоступному предложению.

## 11. Архитектура

Предпочтительная схема:

```text
Frontend
   ↓
TravelHUB Tour Search API
   ↓
Search Orchestrator
   ├── Summer Adapter
   └── Kompas Adapter
          ↓
      Supplier APIs
          ↓
   Normalization Layer
          ↓
   Availability / Deduplication
          ↓
   Sorting / Filtering
          ↓
   Unified Results
          ↓
Frontend Table
          ↓
Offer Details
          ↓
Revalidation
          ↓
Booking
```

Search Orchestrator не должен содержать поставщицкую бизнес-логику.

Summer и Компас должны быть изолированы собственными adapters/services.

## 12. Параллельный поиск и ошибки

Summer и Компас запрашивать параллельно.

Предпочтительно использовать механизм уровня:

```ts
Promise.allSettled(...)
```

или эквивалент.

Пример:

```text
Summer ✓ 124
Компас ✓ 86
Всего 210
```

При ошибке Summer:

```text
Summer — временно недоступен
Компас — результаты доступны
```

При ошибке обоих:

```text
Не удалось получить актуальные предложения.
Попробуйте повторить поиск.
```

Предусмотреть timeout каждого поставщика.

## 15. География и доступность

Использовать:

```text
Справочники
 └── География
      ├── Страны
      ├── Города
      └── Курорты
```

География является мастер-справочником.

У единиц географии должна определяться доступность по категориям.

Например:

```text
Греция
  Tours: YES
  Hotels: YES
  Flights: NO
```

Для туров география доступна только при наличии активных турпредложений.

Если все предложения по городу/курорту исчезли или ушли в архив:

```text
Tours availability = false
```

Город/курорт перестаёт показываться в поиске туров.

Но сама запись географии **не удаляется**.

Если позже появляется новый активный тур:

```text
Tours availability = true
```

география автоматически возвращается в поиск.

## 16. Архивирование

Не смешивать:

```text
География
```

и

```text
Предложение поставщика
```

Архивирование предложения не удаляет географию.

Пример:

```text
Анталья
```

остаётся в справочнике.

Если активных туров нет:

```text
Tours availability = false
```

Если появляется новый тур:

```text
Tours availability = true
```

## 17. Цена и валюта

Хранить:

```text
amount
currency
```

Не выполнять скрытую конвертацию.

Если TravelHUB отображает единую валюту, правила конвертации должны быть централизованными.

Оригинальную цену поставщика сохранять.

## 18. Безопасность

Секреты Summer и Компас не передавать во frontend.

API-ключи, логины, пароли и токены:

```text
Backend only
```

Frontend получает только необходимые данные предложения.

## 19. Производительность

Предусмотреть:

- cancellation;

Кэш не должен выдавать устаревшую цену как живую.

- [ ] строка кликабельна;

### Offer

- [ ] открывается выбранное предложение;
- [ ] отображаются его параметры;
- [ ] отображается цена;
- [ ] есть «Забронировать».

### Booking

- [ ] есть revalidation, если предусмотрен API;
- [ ] изменение цены обрабатывается;
- [ ] недоступное предложение нельзя забронировать;

### Geography

- [ ] используется единый справочник;
- [ ] нет дублирующей географии у поставщиков;
- [ ] отсутствие активных туров скрывает географию из поиска;

- [ ] запись географии не удаляется.

## 24. Ключевой принцип

TravelHUB должен воспринимать Summer и Компас как **источники живого инвентаря**, а не как статические каталоги.

Пользователь задаёт параметры один раз:

```text
Страна
Город
Курорт
Дата
Ночи
Взрослые
Дети
Возраст детей
```

и получает единый актуальный результат:

```text
                 TRAVELHUB
                     │
             Universal Search
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
       SUMMER                КОМПАС
          ↓                     ↓
     Live offers            Live offers
          └──────────┬──────────┘
                     ↓
              Normalization
                     ↓
              Unified Results
                     ↓
               Tour Table
                     ↓
               Offer Card
                     ↓
              Revalidation
                     ↓
                 Booking
```

**Главная цель UX: пользователь не должен думать о том, у какого поставщика находится тур. Он задаёт параметры один раз, получает единый список актуальных предложений и выбирает подходящий вариант.**
