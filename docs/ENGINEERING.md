# Navitravel — инженерный процесс

Практическое соглашение о том, как мы ведём изменения в проекте. Это не замена
`AGENTS.md`, а рабочий регламент для задач, ревью и приёмки.

## 1. Начинаем с поведения

До кода формулируем:

```text
что пользователь/система делает сейчас
что должно происходить после изменения
какие данные проходят через UI → API → сервис → БД
как проверим результат
```

Если поведение не сформулировано, изменение не начинается.

## 2. Выбор навыка

| Задача | Навык |
|---|---|
| NestJS, Prisma, PostgreSQL, миграции | `navitravel-backend` |
| Next.js, React, Tailwind, локализация | `navitravel-frontend` |
| Проверка перед сдачей | `navitravel-verify` |
| Платежи, PII, RBAC, поставщики | `navitravel-security` |
| Ревью diff | `navitravel-review` |

Для UI/дизайна дополнительно используется `frontend-design`, для вопросов об
архитектуре — `graphify`.

## 3. Рабочий цикл

```text
plan → implement → test → review → verify → report
```

1. **Plan** — определить ожидаемое поведение и затронутые контракты.
2. **Implement** — минимальный diff в существующем паттерне.
3. **Test** — точечные тесты на новое поведение и граничные случаи.
4. **Review** — пройти diff по `navitravel-review`, особенно cross-stack контракты.
5. **Verify** — build + реальная проверка API/браузера.
6. **Report** — что изменено, где, чем проверено, что не проверено, коммит.

## 4. Обязательные проверки

Перед коммитом:

```text
backend build, если менялся backend
frontend build, если менялся frontend
targeted tests для затронутой логики
API-проверка для серверных изменений
браузерная проверка для UI/UX
RU/AZ/EN для пользовательских текстов
миграционная проверка для изменений схемы
```

Сборка сама по себе не является доказательством для визуальной или серверной
задачи.

## 5. Границы изменений

- Не менять несвязанные файлы и сгенерированный код.
- Не переписывать существующий паттерн без причины.
- Не удалять данные/колонки/поля без явного требования.
- Не ослаблять RBAC, валидацию или money-gates ради «чтобы работало».
- Не коммитить секреты, пароли, `.env`, токены.

## 6. Финансы и поставщики

- Цены, суммы, статусы и составы пассажиров от клиента не считаются доверенными.
- Сервер должен перепроверять цену перед созданием обязательства.
- Ошибки внешних API не «залипают» в кеше навсегда: нужен TTL/повтор.
- Периоды, валюты, округления и база расчёта должны быть явно указаны.
- Исторические расчёты должны раскрывать точность (`LEGACY_CURRENT` и т.п.).

## 7. Локализация

- Пользовательские строки — RU/AZ/EN.
- Не хардкодить русский текст в новом UI.
- Даты — через существующий `DateTextInput`.
- Технические коды (`TOUR`, `SUMMERTOUR`, `ACTIVE`) не являются локализованным текстом.
- Новые колонки/фильтры проверять на всех трёх языках.

## 8. Живые состояния

Для фоновых процессов и обновлений:

- новая запись появляется без F5;
- активный статус опрашивается только пока он активен;
- терминальные статусы останавливают polling;
- отмена обновляет строку сразу;
- зависший статус можно отменить и увидеть `CANCELLED`.

## 9. Отчёт о готовности

Каждая задача заканчивается явно:

```text
что изменено
где
чем проверено
результат
коммит
что осталось ограничением
```
