# Глава 5. Бронирования (Booking Center)

> Архитектурная документация раздела «Бронирования» платформы TravelHub.
> Уровень детализации: Enterprise SaaS. Документ описывает интерфейс,
> бизнес-логику, жизненный цикл, интеграции и AI-функции раздела.

---

## 5.1 Назначение страницы (Booking Center)

Раздел **Бронирования (Booking Center)** — операционный центр управления всеми бронированиями туристических услуг платформы TravelHub.

### 5.1.1 Роль раздела в платформе

Booking Center является связующим звеном между клиентским спросом и поставщиками услуг:

```
Клиент (сайт/приложение)
        │  создаёт бронирование
        ▼
┌─────────────────────────────┐
│      Booking Center         │
│  подтверждение · оплата ·   │
│  документы · SLA · возвраты │
└─────────────────────────────┘
        │
        ├──► Поставщики (отели, авиакомпании, туроператоры…)
        ├──► CRM / Заказы / Продажи / Финансы
        ├──► Платёжные системы, Email, SMS, Push, WhatsApp, Telegram
        └──► AI-движок (прогнозы, риски, рекомендации)
```

### 5.1.2 Основные задачи

- централизованное создание и обработка бронирований всех категорий услуг;
- контроль статусов бронирования и оплаты в реальном времени;
- управление жизненным циклом бронирования (подтверждение → оплата → документы → завершение);
- контроль SLA и просроченных подтверждений;
- оперативное выявление проблемных бронирований;
- аналитика: конверсия, среднее время подтверждения, динамика, география;
- финансовый контроль: ожидающие платежи, комиссии, выплаты партнёрам;
- AI-поддержка: прогнозы, риск-анализ, рекомендации менеджерам.

### 5.1.3 Кто использует раздел

| Роль | Потребности |
|---|---|
| Booking Manager | обработка броней, подтверждения, работа с поставщиками |
| Sales Manager | конверсия бронь → оплата, работа с клиентами |
| Finance Manager | контроль оплат, возвратов, комиссий |
| Partner Manager | контроль поставщиков и SLA |
| Support Manager | работа с проблемными бронированиями |
| Administrator / Super Admin | полный контроль, настройка, отчёты |
| Read Only | просмотр без изменений (аудит, отчётность) |

### 5.1.4 Какие проблемы решает

- потери бронирований из-за необработанных подтверждений;
- просроченные оплаты без напоминаний;
- отсутствие единой картины по всем каналам (сайт, партнёры, Telegram, WhatsApp);
- ручной контроль SLA;
- отсутствие прогнозов отмен и дохода;
- невозможность быстро найти бронь по любому атрибуту.

### 5.1.5 Ключевые бизнес-процессы

1. Создание бронирования (клиент / менеджер / партнёр / бот).
2. Подтверждение у поставщика.
3. Выставление и приём оплаты.
4. Подготовка и отправка документов (ваучер, договор, чек).
5. Проведение поездки и завершение брони.
6. Отмена / возврат.
7. Работа с проблемными и просроченными бронированиями.

## 5.5 KPI-панель (9 карточек)

| # | Карточка | Формула | Цветовой статус | Детализация | Действия |
|---|---|---|---|---|---|
| 1 | Новые бронирования | `count(status = PENDING)` — бронь «Ожидает подтверждения» | — | `N ожидают подтверждения` | Клик — фильтр `PENDING`; повторный клик сбрасывает |
| 2 | Подтверждённые | `count(status = CONFIRMED)` — подтверждены и ждут оплаты, без оплаченных и завершённых | Синий при росте | `N ждут оплаты` | Клик — фильтр `CONFIRMED`; повторный клик сбрасывает |
| 3 | Ожидают оплаты | `count(оплата = «В ожидании оплаты»)` = `status ∈ {PENDING, CONFIRMED}` | Жёлтый (внимание) | Сумма в ожидании | Клик — фильтр группы `PENDING,CONFIRMED` (селект «Ожидают оплаты (все)»); повторный клик сбрасывает |
| 4 | Оплаченные | `count(оплата = «Оплачена»)` = `status ∈ {PAID, COMPLETED}` (завершённые тоже оплачены) | Зелёный | Сумма оплат | Клик — фильтр группы `PAID,COMPLETED` (селект «Оплаченные (все)»); повторный клик сбрасывает |
| 5 | Отменённые | `count(status = REFUNDED)` | Красный при росте | Сумма возвратов | Клик — фильтр `REFUNDED`; повторный клик сбрасывает |
| 6 | Завершённые | `count(status = COMPLETED)` | Зелёный при росте | `N из M оплаченных завершено` + мини-прогресс-бар завершённости (доля `COMPLETED` от `PAID + COMPLETED`) | Клик — фильтр `COMPLETED`; повторный клик сбрасывает |
| 7 | Требуют внимания | `count(брони с непрочитанными сообщениями)` | Красный при росте | Непрочитанных сообщений всего | Клик — переключение фильтра `needsAttention` в панели фильтрации (карточка подсвечивается) |
| 8 | Конверсия бронь→оплата | `оплачено / всего × 100%` | Зелёный ≥ 60% | `оплачено из N броней` | Клик → воронка (планируется) |
| 9 | Прогноз AI | `count × 1.18`, риск отмен | Нейтральный | Доход, риск отмен % | Клик → AI-панель (планируется) |

> **Среднее время подтверждения** (`avg(updatedAt − createdAt)` для оплаченных) вынесено из KPI-карточек и отображается строкой в виджете **«🎯 Контроль SLA»** (рядом с соблюдением SLA и просроченными подтверждениями).

**KPI считаются по полному периоду:** значения всех карточек не зависят от активного фильтра статуса — клик по карточке «Отменённые» (или выбор статуса в селекте/быстром фильтре) фильтрует только таблицу, а остальные карточки сохраняют свои значения по периоду. Фильтр `status` применяется к таблице в памяти (как `needsAttention`, `manager`, `source`), не влияя на KPI, графики и виджеты.

**Воронка конверсии (под KPI-карточками):** визуализация жизненного цикла брони по накопительным этапам — **создано → подтверждено → оплачено** (не путать с текущими статусами карточек):

| Этап | Условие (накопительное) | Пример (месяц) |
|---|---|---|
| Новые бронирования (вход) | `count(createdAt ∈ период)` — все брони периода | 57 |
| Подтверждённые | `count(status ∈ {CONFIRMED, PAID, COMPLETED})` — дошли до подтверждения | 46 |
| Оплаченные | `count(status ∈ {PAID, COMPLETED})` — дошли до оплаты | 35 |

Между этапами показывается процент перехода (46/57 = 81% → 35/46 = 76%), внизу — итоговая конверсия до оплаты (61%). Данные приходят с API в поле `funnel = { entry, confirmed, paid }`.

**Взаимоисключение карточек:** клик по любой кликабельной карточке (1–7) снимает активность остальных — карточка статуса (1–6) сбрасывает `needsAttention`, а «Требуют внимания» сбрасывает `status`. Это исключает пустые комбинации фильтров (например, «Отменённые» + «Требуют внимания»). Повторный клик по активной карточке снимает её фильтр полностью. Активная карточка подсвечивается рамкой/кольцом основного цвета, у кликабельных карточек есть подсказка-бейдж «⇣ фильтр» (у активной — «✕ снять»). То же правило действует при ручном выборе в селектах «Статус бронирования» / «Переписка» и в быстрых фильтрах («Возвраты», «💬 Требуют внимания» и т. п.): установка одного фильтра сбрасывает противоположный.

## 5.6 Панель фильтрации

### Фильтры

- **период** (сегодня / вчера / неделя / месяц / квартал / год / произвольный);
- **страна** — все страны из БД (активные услуги, справочник `/api/countries`); **город** — каскадный, как в каталоге услуг: доступен после выбора страны и показывает только города этой страны (`/api/cities?countries=…`), при смене страны выбранный город сбрасывается; **направление**;
- **категория услуги** (туры, отели, санатории, авиа, Ж/Д, экскурсии, гиды, трансферы, фотографы);
- **партнёр**; **поставщик**; **менеджер**;
- **статус бронирования** (PENDING / CONFIRMED / PAID / REFUNDED / COMPLETED — раздельно; две группы для карточек по оплате: «Ожидают оплаты (все)» = `PENDING,CONFIRMED` и «Оплаченные (все)» = `PAID,COMPLETED` — выбираются кликом по KPI-карточкам «Ожидают оплаты»/«Оплаченные»); применяется только к таблице — KPI-карточки и виджеты считаются по полному периоду;
- **статус оплаты** (оплачен / ожидает / возврат);
- **«Требуют внимания»** — только брони с непрочитанными сообщениями переписки (`needsAttention=1`, бейдж `💬 N` > 0); доступен как быстрый фильтр и как поле «Переписка» в сетке фильтров;
- **источник бронирования** (сайт, приложение, партнёр, call-центр, Telegram-бот, WhatsApp);
- **валюта**; **диапазон стоимости** (мин/макс).

### Дополнительные возможности

- **сохранение фильтров** — кнопка «💾 Сохранить» фиксирует текущую комбинацию;
- **шаблоны фильтров** — именованные наборы (например, «Возвраты за месяц»);
- **быстрые фильтры** — пресеты: «Ожидают оплаты», «Оплачено сегодня», «Просроченные», «Возвраты».

### Возможности

- **индикация активных фильтров** — под заголовком таблицы показываются чипы применённых фильтров/селектов: чип «Период: …» отображается всегда, остальные (страна, город, категория, статус, оплата, менеджер, источник, валюта, стоимость, «Требуют внимания», поиск) — по мере применения; клик по ✕ сбрасывает конкретный фильтр (для страны сбрасывается и город), поиск — очисткой запроса;
  - реализовано **общим компонентом `src/components/admin/ActiveFilterChips.tsx`**, который используется также в **Sales Center** (под заголовком «Таблица продаж») и в **Analytics** (внутри панели фильтров): там отображаются чипы периода, страны, города, категории/услуги, партнёра, статуса и поиска с тем же поведением ✕;
- **сортировка** — по клику на заголовок (клиент, сумма, даты, статус); колонка «Переписка» сортирует по числу непрочитанных сообщений по убыванию (`sort=unread`);
- **поиск** — мгновенный фильтр по № брони, заказу, клиенту, услуге, направлению, поставщику;
- **фильтрация** — серверная по всем параметрам панели фильтрации;
- **группировка** — по категории/статусу/менеджеру (планируется);
- **массовые действия** — выбор строк чекбоксами (в т.ч. «выбрать все на странице» с промежуточным состоянием) → панель «Выбрано: N» с кнопками «Подтвердить / На оплату / Отменить» → `POST /api/admin/bookings/bulk`; недопустимые статусы пропускаются с подсчётом, каждая операция пишется в журнал истории;
- **экспорт** — CSV с BOM (UTF-8), разделитель «;»;
- **счётчик «требует внимания»** — колонка «Переписка»: бейдж `💬 N` с числом непрочитанных system/manager сообщений (сбрасывается при открытии переписки в карточке); строка с непрочитанными сообщениями подсвечивается лёгкой красной подложкой и жирным шрифтом;
- **настройка колонок** — выбор и порядок колонок (планируется);
- **пагинация** — 15 строк на страницу, согласована с фильтрами.

## 5.10 Жизненный цикл бронирования

```
Черновик → Создано → Ожидает подтверждения → Подтверждено
        → Ожидает оплаты → Оплачено → Подготовка документов → Завершено
```

| Статус (БД) | Жизненный цикл | Условия перехода | Автоматические действия | Уведомления |
|---|---|---|---|---|
| PENDING | Ожидает подтверждения | создание брони | постановка в очередь подтверждения | Клиенту: «бронь принята» |
| CONFIRMED | Подтверждено | действие `confirm` | включение таймера оплаты (SLA) | Клиенту: «подтверждено, ожидается оплата» |
| PAID | Оплачено | действие `pay` | генерация документов | Клиенту: чек; поставщику: подтверждение оплаты |
| REFUNDED | Возвращено | действие `cancel` | инициация возврата | Клиенту: возврат; финансам: операция |
| COMPLETED | Завершено | действие `complete` | закрытие брони, запрос отзыва | Архив |

**Дополнительные статусы** (уровень Enterprise): «Частично оплачено», «Изменено», «Истек срок действия» — зарезервированы в схеме жизненного цикла для будущих релизов.

**Ограничения переходов:** недопустимый переход возвращает `409 Conflict` с пояснением (например, `COMPLETED → confirm`).

## 5.15 API

### GET `/api/admin/bookings`

Параметры: `period, from, to, country, city, type, partnerId, providerId, status, paymentStatus, manager, source, currency, minPrice, maxPrice, needsAttention, search, page, limit`.

`status` принимает один статус (`PENDING`, `CONFIRMED`, `PAID`, `REFUNDED`, `COMPLETED`) или список через запятую (например, `status=PENDING,CONFIRMED` — группа «Ожидают оплаты», `status=PAID,COMPLETED` — группа «Оплаченные», устанавливаются кликом по KPI-карточкам, Гл. 5.5). Фильтр применяется **только к таблице** (`bookings`/`pagination`): KPI-карточки, графики и виджеты всегда считаются по полному периоду и не обнуляются при выборе статуса.

`needsAttention=1` — возвращает только брони с непрочитанными сообщениями (`unreadCount > 0`), согласован с пагинацией и остальными фильтрами.

`sort=unread` — сортировка по числу непрочитанных сообщений по убыванию (до пагинации, согласована со страницами и `total`).

Ответ: `kpi` (9 карточек, включая `needsAttention`: брони с непрочитанными сообщениями за период и их изменение к предыдущему), `bookingsSeries`, `bookingsByService`, `bookingsByCountry`, `heatmap`, `confirmSeries`, `financial`, `recentBookings`, `problemBookings`, `pendingPayments`, `upcomingTrips`, `overdueConfirmations`, `sla`, `providerNotifications`, `aiRecommendations`, `bookings`, `pagination`.

### GET `/api/admin/bookings?mode=form`

Режим справочников для формы «Создать бронирование». Возвращает:

- `clients` — активные покупатели (`role = BUYER`, до 200): `{ id, name, email }`;
- `services` — активные услуги (до 300): `{ id, type, category, title, price, currency, direction }`, где `price` = `discountPrice ?? price`.

### POST `/api/admin/bookings`

Создание бронирования через форму Booking Center.

Тело: `{ "userId": string, "serviceId": string, "serviceDate": ISO-дата, "amount"?: number, "source"?: string }`.

Правила:

- клиент и услуга обязательны, клиент должен быть `BUYER`, услуга — активной;
- `serviceDate` обязательна и должна быть корректной датой;
- `amount` берётся из тела (если > 0) либо из цены услуги со скидкой;
- новая бронь создаётся со статусом **PENDING** («Ожидает подтверждения»).

Ответ `201`: `{ ok, message, booking: BookingRow }` (BookingRow — строка таблицы с `bookingNumber`, `orderId`, `paymentStatus: "pending"`, `source: "Создано в админке"`).
Ошибки: `400` невалидное тело/даты, `404` клиент или услуга не найдены, `401` без авторизации.

### POST `/api/admin/bookings/bulk`

Массовые действия над несколькими бронированиями (Гл. 5.8).

Тело: `{ "action": "confirm" | "pay" | "cancel", "ids": string[] }` (до 100 id, дубликаты удаляются).

- `confirm`: `PENDING → CONFIRMED`;
- `pay`: `PENDING|CONFIRMED → PAID`;
- `cancel`: `PENDING|CONFIRMED|PAID → REFUNDED`.

Брони, для которых переход недопустим в текущем статусе, пропускаются. Все операции выполняются в одной транзакции, каждая — с записью в журнал истории (`actorName` = текущий администратор).

Ответ: `{ ok, message, processed, skipped }`.
Ошибки: `400` недопустимое действие или пустой `ids`, `401` без авторизации.

### GET `/api/admin/bookings/[id]/history`

Журнал изменений бронирования (вкладка «История» в карточке). Возвращает `{ history: [...] }` — записи от новых к старым: `{ id, action, from, to, fields, actorName, comment, createdAt }`.

- `action`: `created | confirm | pay | complete | cancel | update`;
- `from`/`to` — статусы для переходов, `fields` — изменённые поля для `update` (`{ amount?, serviceDate? }`);
- `actorName` — исполнитель (администратор/менеджер/клиент).

Записи создаются атомарно вместе с изменением брони (транзакция): `POST` пишет `created`, `PATCH` пишет запись о переходе или правке. Ошибки: `404` бронь не найдена, `401` без авторизации.

### GET `/api/admin/bookings/[id]/messages`

Переписка по бронированию (вкладка «Переписка» в карточке). Возвращает `{ messages: [...] }` — от старых к новым: `{ id, senderName, senderRole: "manager" | "client", text, createdAt }` (детерминированный порядок: при равном `createdAt` — по `id`). Ошибки: `404` бронь не найдена, `401` без авторизации.

### POST `/api/admin/bookings/[id]/messages`

Отправка сообщения в переписку брони.

Тело: `{ "text": string, "asClient"?: boolean }`.

- `text` обязателен (до 2000 символов, `400` иначе);
- по умолчанию сообщение от **менеджера** (текущий администратор), при `asClient: true` — от **клиента** (демо-режим);
- запись сохраняется в БД (`BookingMessage`).

Ответ `201`: `{ ok, message, item: Message }`. Ошибки: `400` пустой/длинный текст, `404` бронь не найдена, `401` без авторизации.

### POST `/api/admin/bookings/[id]/messages/read`

Помечает все непрочитанные сообщения брони (`senderRole = system/manager`, `isRead = false`) как прочитанные — сбрасывает счётчик «требует внимания» на вкладке и в таблице. Вызывается при открытии вкладки «Переписка» в карточке. Ответ: `{ ok, marked }` (`marked` — количество помеченных). Ошибки: `404` бронь не найдена, `401` без авторизации.

Поля ответа `GET /api/admin/bookings/[id]/messages`: каждое сообщение содержит `isRead`; верхнеуровневый `unreadCount` — количество непрочитанных system/manager сообщений брони. В `GET /api/admin/bookings` каждая строка таблицы содержит `unreadCount` (колонка «Переписка»).

### Автоматические системные сообщения (Гл. 5.9)

При смене статуса бронирования в переписку автоматически добавляется системное сообщение (`senderRole = "system"`, `senderName = "Система"`) — атомарно, в той же транзакции, что и смена статуса:

- **создание** (POST) — «Бронирование создано и ожидает подтверждения»;
- **confirm** — «Бронирование подтверждено ✅»;
- **pay** — «Оплата получена 💳»;
- **complete** — «Поездка завершена 🎉»;
- **cancel** — «Бронирование отменено, средства возвращены ↩️».

Массовые действия (`POST /api/admin/bookings/bulk`) пишут системные сообщения для каждой обработанной брони. В карточке переписка перезагружается после каждого действия, поэтому системные сообщения появляются в чате сразу.

### PATCH `/api/admin/bookings/[id]`

Тело: `{ "action": "confirm" | "pay" | "cancel" | "complete" | "update", "serviceDate"?: ISO, "amount"?: number }`.

- `confirm`: `PENDING → CONFIRMED`;
- `pay`: `CONFIRMED|PENDING → PAID`;
- `complete`: `PAID → COMPLETED`;
- `cancel`: `PENDING|CONFIRMED|PAID → REFUNDED`;
- `update`: правка **даты поездки** и/или **суммы** (без смены статуса):
  - минимум одно поле обязательно (`400` иначе);
  - `amount` > 0 и конечен; `serviceDate` корректна и не в прошлом;
  - редактирование брони со статусом `REFUNDED` запрещено (`409`);
  - ответ `{ ok, message, booking: BookingRow }` — полная обновлённая строка таблицы.

Ответ (статусные действия): `{ ok, booking: { id, status, from, amount, updatedAt }, message }`.
Ошибки: `400` недопустимое действие/поля, `404` бронь не найдена, `409` недопустимый переход или правка возвращённой брони, `401` без авторизации.

### Форма редактирования (UI)

Кнопка «✏️ Изменить бронирование» (Гл. 5.4) и кнопка «Изменить даты и сумму» в карточке брони открывают модальное окно:

1. предзаполненные **дата поездки** и **сумма** (валюта брони);
2. сохранение отправляет только изменённые поля (`action: "update"`);
3. после сохранения — тост, обновление таблицы/виджетов и открытой карточки бронирования.

Кнопка недоступна для броней со статусом `REFUNDED`.

### Форма создания (UI)

Кнопка «➕ Создать бронирование» (Гл. 5.4) открывает модальное окно:

1. выбор **клиента** (справочник `?mode=form`);
2. выбор **категории** (чипы) и **услуги** (цена услуги подставляется в поле суммы, сумма редактируема);
3. **дата поездки** (мин. — завтра) и **сумма** в USD;
4. «Создать бронирование» → `POST` → тост об успехе, таблица и виджеты обновляются автоматически.

После создания бронь сразу доступна для подтверждения/оплаты через PATCH-эндпоинт.
