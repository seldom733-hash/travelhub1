> Архитектурная документация раздела «Заказы» платформы TravelHub.
> Уровень детализации: Enterprise SaaS. Документ описывает интерфейс,
> бизнес-логику, жизненный цикл, интеграции и AI-функции раздела.

## 7.1 Назначение страницы (Order Center)

Раздел **Заказы (Order Center)** — операционный центр управления всеми заказами клиентов платформы TravelHub.

### 7.1.1 Роль заказа в платформе

**Заказ — центральная бизнес-сущность платформы.** В отличие от бронирования (единичная заявка на одну услугу), заказ объединяет клиента, одну или несколько услуг (через входящие в заказ бронирования), платежи, документы, партнёров, поставщиков, менеджеров и историю взаимодействий. Заказ — это «конверт», в котором ведётся вся работа с конкретным путешествием клиента: от создания до завершения поездки.

```
Клиент (сайт / приложение / партнёр / call-центр / Telegram / WhatsApp)
        │  создаёт заказ (в составе — бронирования услуг)
        ▼
┌─────────────────────────────────────────────┐
│               Order Center                  │
│  подтверждение · оплата · документы ·       │
│  SLA · возвраты · коммуникации · история    │
└─────────────────────────────────────────────┘
        │
        ├──► Бронирования (Booking Center) — позиции заказа
        ├──► Продажи (Sales Center) — оплаченные заказы формируют выручку
        ├──► Финансы — комиссия 12%, выплаты партнёрам 88%
        ├──► Партнёры и поставщики услуг
        ├──► Платёжные системы, Email, SMS, Push, WhatsApp, Telegram
        └──► AI-движок (прогнозы, риски, рекомендации)
```

### 7.1.2 Связь заказа с другими сущностями

| Сущность | Связь с заказом |
|---|---|
| Бронирования | Заказ содержит одну или несколько броней (`Booking.orderId`). Статус брони в заказе — «худший» из входящих (от PENDING до REFUNDED). Колонка «Статус бронирования» в таблице заказов |
| Продажи | Оплаченные заказы (PAID, DOCUMENT_PREP, READY, COMPLETED) формируют выручку Sales Center |
| Финансы | Комиссия платформы **12%** от оплаченной суммы, выплаты партнёрам **88%** |
| Клиенты | Заказ принадлежит пользователю (`Order.userId`); в карточке — клиент, его контакты и история |
| Партнёры / Поставщики | Услуги в составе заказа предоставляются поставщиками; партнёр — компания-источник |
| Платежи | `Order.amount` (стоимость), `Order.paidAmount` (оплачено); статус оплаты выводится из статуса заказа |
| Документы | Ваучер, договор оферты, чек об оплате (готовность зависит от статуса оплаты) |
| CRM | Журнал изменений (`OrderHistory`) и переписка (`OrderMessage`) по каждому заказу |
| Аналитика | KPI, графики, география, тепловая карта активности по заказам |

### 7.1.3 Что такое заказ и его отличие от бронирования и продажи

- **Заказ** — агрегат жизненного цикла клиентской поездки: клиент + состав услуг (брони) + платежи + документы + коммуникации + история. Имеет собственный номер `ORD-{N}` и последовательность статусов (Гл. 7.10).
- **Бронирование** — единичная заявка на одну услугу со своим жизненным циклом `PENDING → CONFIRMED → PAID → COMPLETED` (или `REFUNDED`). В заказе может быть несколько броней (несколько услуг поездки).
- **Продажа** — факт признания выручки. Заказ становится продажей после оплаты; неоплаченный заказ — ещё не продажа. Один заказ = одна продажа, но продажа всегда привязана к заказу.

### 7.1.4 Жизненный цикл заказа (кратко)

```
Черновик → Создан → В обработке → Ожидает подтверждения → Подтверждён
        → Ожидает оплаты → Частично оплачен → Оплачен → Подготовка документов
        → Готов к поездке → Завершён
Дополнительно: Изменён · Возвращён · Отменён · Просрочен · Архивирован
```

Подробно — в Гл. 7.10.

### 7.1.5 Кто использует раздел

| Роль | Потребности |
|---|---|
| Order Manager | создание и обработка заказов, подтверждения, документы |
| Sales Manager | конверсия заказ → оплата, работа с клиентами |
| Finance Manager | контроль оплат, возвратов, комиссий |
| Partner Manager | контроль поставщиков и SLA |
| Support Manager | работа с проблемными и просроченными заказами |
| Administrator / Super Admin | полный контроль, настройка, отчёты |
| Read Only | просмотр без изменений (аудит, отчётность) |

### 7.1.6 Какие проблемы решает

- потеря заказов из-за необработанных подтверждений и просроченных оплат;
- отсутствие единой картины по всем каналам (сайт, приложение, партнёры, call-центр, Telegram, WhatsApp);
- ручной контроль SLA и сроков обработки;
- невозможность быстро найти заказ по любому атрибуту;
- отсутствие прогнозов отмен, выручки и рисков;
- потеря контекста: кто клиент, какие услуги куплены, сколько оплачено, какие документы готовы.

### 7.1.7 Задачи пользователя

| Задача | Описание |
|---|---|
| Создание заказов | мастер «Создать заказ»: клиент → категория → услуга → дата → сумма |
| Управление заказами | подтверждение, оплата, завершение, отмена, возврат, архивация |
| Контроль исполнения | статусы заказов, SLA, просроченные действия, проблемные заказы |
| Контроль оплат | ожидающие оплаты, частичные оплаты, возвраты, финансовые показатели |
| Контроль документов | ваучер, договор, чек; готовность по статусу оплаты |
| Контроль возвратов | возвраты с суммами, работа с причинами отмен |
| Управление коммуникациями | переписка с клиентом по заказу, системные уведомления о смене статусов |

## 7.5 KPI-панель (8 карточек)

| # | Карточка | Формула | Цветовой статус | Детализация | Действия |
|---|---|---|---|---|---|
| 1 | Новые заказы | `count(status ∈ {DRAFT, CREATED, AWAITING_CONFIRMATION})` | Синий при росте | `N всего за период` | Клик — фильтр `AWAITING_CONFIRMATION`; повторный клик сбрасывает |
| 2 | Активные заказы | `count(активные статусы)` — DRAFT…OVERDUE без терминальных | Голубой при росте | `N в обработке` (PROCESSING) | — |
| 3 | Ожидают оплаты | `count(status ∈ {AWAITING_PAYMENT, PARTIALLY_PAID, OVERDUE})` | Жёлтый (внимание) | Сумма в ожидании | Клик — фильтр группы `AWAITING_PAYMENT,PARTIALLY_PAID,OVERDUE`; повторный клик сбрасывает |
| 4 | Оплаченные заказы | `count(status ∈ {PAID, DOCUMENT_PREP, READY, COMPLETED})` | Зелёный | Сумма оплат + средний чек | Клик — фильтр группы `PAID,DOCUMENT_PREP,READY,COMPLETED`; повторный клик сбрасывает |
| 5 | Отменённые | `count(status = CANCELLED)` | Красный при росте | Доля от всех заказов, % | Клик — фильтр `CANCELLED`; повторный клик сбрасывает |
| 6 | Средний цикл заказа | `avg(updatedAt − createdAt)` по оплаченным/завершённым, в часах | Нейтральный | `Цель SLA: 48 ч · Соблюдение N%` + мини-прогресс-бар цикла (доля от цели SLA) | — |
| 7 | Возвраты | `count(status = REFUNDED)` | Оранжево-красный | Сумма возвратов | Клик — фильтр `REFUNDED`; повторный клик сбрасывает |
| 8 | AI-прогноз | `заказы месяца × 1.18`, риск отмен | Нейтральный | Ожидаемая выручка, план % | Клик → AI-панель (планируется) |

> **Примечание о составе карточек.** По техническому заданию раздел предусматривал отдельную карточку «Заказы в обработке». В реализации количество «в обработке» (`PROCESSING`) показывается детализацией карточки **«Активные заказы»**, а освободившееся место занимает карточка **«Возвраты»** (критичная для финансового контроля). Дополнительно API возвращает показатель `needsAttention` (заказы с непрочитанными сообщениями переписки), который выведен в фильтр и колонку таблицы «Требуют внимания».

**KPI считаются по полному периоду:** значения карточек не зависят от активного фильтра статуса — клик по карточке фильтрует только таблицу, остальные карточки сохраняют значения по периоду. Фильтр `status` применяется к таблице в памяти, не влияя на KPI, графики и виджеты.

**Взаимоисключение карточек:** клик по кликабельной карточке (1, 3, 4, 5, 7) снимает активность остальных; повторный клик по активной карточке снимает её фильтр полностью. Активная карточка подсвечивается рамкой/кольцом основного цвета, у кликабельных карточек есть бейдж «⇣ фильтр» (у активной — «✕ снять»). То же правило действует при выборе статуса в селектах фильтрации.

## 7.6 Панель фильтрации

### Фильтры

- **период** — сегодня / вчера / неделя / месяц / квартал / год (пресеты); произвольный диапазон поддерживается API (`from`/`to`);
- **страна** — справочник стран; **город** — каскадный: доступен после выбора страны и показывает только города этой страны (`/api/cities?countries=…`), при смене страны выбранный город сбрасывается;
- **партнёр** — компания-источник заказа; **поставщик** — поставщик услуги (`providerId` = `partnerId` при отсутствии поставщика);
- **менеджер** — детерминированная ротация по `id` заказа;
- **категория услуги** — туры, отели, санатории, авиа, Ж/Д, экскурсии, гиды, трансферы, фотографы;
- **статус заказа** — все статусы жизненного цикла (Гл. 7.10) + две группы: «Ожидают оплаты (все)» = `AWAITING_PAYMENT,PARTIALLY_PAID,OVERDUE` и «Оплаченные (все)» = `PAID,DOCUMENT_PREP,READY,COMPLETED` (выбираются кликом по KPI-карточкам);
- **статус бронирования** — `PENDING / CONFIRMED / PAID / REFUNDED / COMPLETED` (по «худшей» брони в заказе);
- **статус оплаты** — оплачен / частично / ожидает / возврат (производный от статуса заказа);
- **валюта** — USD, EUR, AZN, RUB;
- **источник продажи** — сайт, мобильное приложение, партнёр, call-центр, Telegram-бот, WhatsApp;
- **диапазон стоимости** — мин/макс;
- **«Требуют внимания»** — только заказы с непрочитанными сообщениями переписки (`needsAttention=1`), совместимо с кнопкой сортировки `sort=unread`.

| ♻️ Сбросить | Сброс всех фильтров к значениям по умолчанию |
| 💾 Сохранить фильтр | Фиксация текущей комбинации как именованного чипа («Период · Статус · внимание») |
| Загрузить шаблон | Применение сохранённого набора фильтров (сохранённые чипы кликабельны; ✕ удаляет) |

Под заголовком таблицы показываются **чипы активных фильтров** (общий компонент `src/components/admin/ActiveFilterChips.tsx`, используется также в Booking Center, Sales Center и Analytics): период, страна, город, категория, статус заказа, статус брони, оплата, менеджер, источник, валюта, стоимость, «Требуют внимания», поиск. Клик по ✕ сбрасывает конкретный фильтр (для страны сбрасывается и город).

| Ближайшие поездки | Оплаченные заказы с датой поездки в ближайшие 30 дней | Открыть карточку | Календарь |
| Контроль SLA | Соблюдение регламентов %, цель 48 ч, просрочено из всего (прогресс-бар с цветовой индикацией ≥80% / ≥50% / <50%) | — | SLA-отчёт |

> **Мониторинг проблемных заказов** (по ТЗ) выведен в левую колонку («Проблемные заказы»), а просроченные действия (`OVERDUE` и ожидающие оплаты с датой ≤ 24 ч) поступают с API и питают AI-рекомендации и уведомления.

## 7.10 Жизненный цикл заказа

```
Черновик → Создан → В обработке → Ожидает подтверждения → Подтверждён
        → Ожидает оплаты → Частично оплачен → Оплачен → Подготовка документов
        → Готов к поездке → Завершён
```

| Статус (БД) | Жизненный цикл | Условия перехода (действие) | Автоматические действия | Системное сообщение |
|---|---|---|---|---|
| DRAFT | Черновик | создание (резерв) | — | — |
| CREATED | Создан | создание | постановка в очередь | «Заказ создан и передан в работу» |
| PROCESSING | В обработке | приём в работу | — | «Заказ принят в обработку» |
| AWAITING_CONFIRMATION | Ожидает подтверждения | создание заказа (реализация) | — | «Заказ создан и ожидает подтверждения» |
| CONFIRMED | Подтверждён | `confirm` из AWAITING_CONFIRMATION/PROCESSING | включение таймера SLA | «Заказ подтверждён ✅» |
| AWAITING_PAYMENT | Ожидает оплаты | выставление счёта | напоминания об оплате | «Ожидается оплата заказа» |
| PARTIALLY_PAID | Частично оплачен | частичный платёж | — | «Частичная оплата получена 💳» |
| PAID | Оплачен | `pay` из CONFIRMED/AWAITING_PAYMENT/PARTIALLY_PAID (`paidAmount = amount`) | генерация документов | «Заказ оплачен 💳» |
| DOCUMENT_PREP | Подготовка документов | подготовка ваучера | — | «Готовятся документы 📄» |
| READY | Готов к поездке | документы готовы | — | «Заказ готов к поездке 🎒» |
| COMPLETED | Завершён | `complete` из PAID/DOCUMENT_PREP/READY | закрытие, запрос отзыва | «Заказ завершён 🎉» |

**Дополнительные статусы:**

| Статус | Правила перехода |
|---|---|
| CHANGED | `update` из CREATED (правка даты/суммы) — «Заказ изменён ✏️» |
| REFUNDED | `refund` из PAID/PARTIALLY_PAID/DOCUMENT_PREP/READY/AWAITING_PAYMENT (`paidAmount = 0`) — «Оформлен возврат ↩️» |
| CANCELLED | `cancel` из активных статусов (DRAFT…OVERDUE) — «Заказ отменён ❌» |
| OVERDUE | просрочка оплаты/подтверждения (расчётная метка) — «Заказ просрочен — требуется действие ⏰» |
| ARCHIVED | `archive` из COMPLETED/CANCELLED/REFUNDED — «Заказ архивирован 📦» |

**Ограничения переходов:** недопустимый переход возвращает `409 Conflict` с пояснением (например, `confirm` для заказа в статусе PAID). Закрытый заказ (COMPLETED/REFUNDED/CANCELLED/ARCHIVED) нельзя редактировать (`409`). Каждый переход атомарно пишет запись в `OrderHistory` и системное сообщение в `OrderMessage` (одна транзакция).

## 7.15 API

### GET `/api/admin/orders`

Параметры: `period, from, to, country, city, type, partnerId, providerId, status, bookingStatus, paymentStatus, manager, source, currency, minPrice, maxPrice, needsAttention, sort, search, page, limit`.

- `status` принимает один статус или список через запятую (группы «Ожидают оплаты (все)» / «Оплаченные (все)» устанавливаются кликом по KPI-карточкам, Гл. 7.5). Фильтр применяется **только к таблице** (`orders`/`pagination`): KPI-карточки, графики и виджеты считаются по полному периоду.
- `providerId` = `partnerId`, если поставщик не указан.
- `needsAttention=1` — только заказы с непрочитанными сообщениями; `sort=unread` — сортировка по числу непрочитанных по убыванию (до пагинации, согласована с `total`).
- Фильтры страны/города/категории/поставщика применяются через входящие в заказ брони; статусы/оплата/менеджер/источник/валюта/стоимость/поиск — после выборки.

Ответ: `kpi` (8 карточек + `needsAttention`), `funnel { entry, confirmed, paid }`, `ordersSeries`, `confirmSeries`, `bookingsByService`, `bookingsByCountry`, `heatmap`, `financial`, `statusCounts`, `recentOrders`, `problemOrders`, `overdueActions`, `pendingPayments`, `refunds`, `upcomingTrips`, `providerNotifications`, `aiRecommendations`, `sla`, `managers`, `orders`, `pagination`, `period`.

### GET `/api/admin/orders?mode=form`

Режим справочников для формы «Создать заказ»: `clients` (активные покупатели `BUYER`, до 200: `{ id, name, email }`) и `services` (активные услуги, до 300: `{ id, type, category, title, price, currency, direction }`, `price` = `discountPrice ?? price`).

### POST `/api/admin/orders`

Создание заказа.

Тело: `{ "userId": string, "serviceId": string, "serviceDate": ISO, "amount"?: number, "source"?: string }`.

Правила:

- клиент и услуга обязательны, клиент — `BUYER`, услуга — активная;
- `serviceDate` обязательна, корректна и не в прошлом;
- `amount` берётся из тела (если > 0) либо из цены услуги со скидкой;
- заказ создаётся со статусом **AWAITING_CONFIRMATION**, номером `ORD-{N}` (N = последний + 1), `paidAmount = 0`;
- в той же транзакции создаётся **первая бронь** заказа (`PENDING`), пишутся записи `created` в журнал брони и заказа и системное сообщение.

Ответ `201`: `{ ok, message, order }`. Ошибки: `400` невалидное тело/даты, `404` клиент/услуга не найдены, `401` без авторизации.

### GET `/api/admin/orders/[id]`

Полная карточка заказа: заказ + клиент (контакты) + брони с услугами и поставщиками + `financial` (сумма/оплачено/остаток/комиссия/выплаты). Ошибки: `404` заказ не найден, `401`.

### PATCH `/api/admin/orders/[id]`

Тело: `{ "action": "confirm" | "pay" | "complete" | "cancel" | "refund" | "archive" | "update", "serviceDate"?: ISO, "amount"?: number }`.

- `confirm`: `AWAITING_CONFIRMATION|PROCESSING → CONFIRMED`;
- `pay`: `CONFIRMED|AWAITING_PAYMENT|PARTIALLY_PAID → PAID` (`paidAmount = amount`);
- `complete`: `PAID|DOCUMENT_PREP|READY → COMPLETED`;
- `cancel`: активные статусы → `CANCELLED`;
- `refund`: `PAID|PARTIALLY_PAID|DOCUMENT_PREP|READY|AWAITING_PAYMENT → REFUNDED` (`paidAmount = 0`);
- `archive`: `COMPLETED|CANCELLED|REFUNDED → ARCHIVED`;
- `update`: правка **даты поездки** и/или **суммы** без смены статуса; минимум одно поле обязательно (`400`), закрытый заказ редактировать нельзя (`409`).

Каждый переход выполняется в транзакции: обновление + запись в `OrderHistory` + системное сообщение в `OrderMessage`. Ответ: `{ ok, message, order }`. Ошибки: `400`, `404`, `409`, `401`.

### GET `/api/admin/orders/[id]/history`

Журнал изменений заказа (вкладка «История»). Возвращает `{ history: [...] }` — записи от новых к старым: `{ id, action, from, to, fields, actorName, comment, createdAt }`. `action`: `created | process | confirm | pay | docs | ready | complete | update | refund | cancel | archive`; `fields` — изменённые поля для `update` (`{ amount?, serviceDate? }`). Ошибки: `404`, `401`.

### GET `/api/admin/orders/[id]/messages`

Переписка по заказу (вкладка «Коммуникации»). Возвращает `{ messages: [...], unreadCount }` — сообщения от старых к новым: `{ id, senderName, senderRole: "manager" | "client" | "system", text, isRead, createdAt }` (детерминированный порядок: при равном `createdAt` — по `id`). `unreadCount` — число непрочитанных system/manager сообщений. Ошибки: `404`, `401`.

### POST `/api/admin/orders/[id]/messages`

Отправка сообщения.

Тело: `{ "text": string, "asClient"?: boolean }`.

- `text` обязателен (до 2000 символов, `400` иначе);
- по умолчанию сообщение от **менеджера** (текущий администратор), при `asClient: true` — от **клиента** (демо-режим).

Ответ `201`: `{ ok, message, item }`. Ошибки: `400`, `404`, `401`.

### POST `/api/admin/orders/[id]/messages/read`

Помечает все непрочитанные сообщения заказа (`senderRole = system/manager`) как прочитанные — сбрасывает счётчик «требует внимания» в таблице и на вкладке. Вызывается при открытии вкладки «Коммуникации». Ответ: `{ ok, marked }`. Ошибки: `404`, `401`.

### POST `/api/admin/orders/bulk`

Массовые действия (Гл. 7.8).

Тело: `{ "action": "confirm" | "pay" | "complete" | "cancel" | "archive", "ids": string[] }` (до 100 id, дубликаты удаляются).

Действия соответствуют переходам PATCH (для `pay` — `paidAmount = amount`). Заказы, для которых переход недопустим, пропускаются. Все операции в одной транзакции, каждая — с записью в журнал истории и системным сообщением.

Ответ: `{ ok, message, processed, skipped }`. Ошибки: `400`, `401`.

### Автоматические системные сообщения (Гл. 7.9)

При смене статуса заказа в переписку автоматически добавляется системное сообщение (`senderRole = "system"`, `senderName = "Система"`) — атомарно, в той же транзакции:

- создание — «Заказ создан и ожидает подтверждения»;
- `confirm` — «Заказ подтверждён ✅»;
- `pay` — «Заказ оплачен 💳»;
- `complete` — «Заказ завершён 🎉»;
- `refund` — «Оформлен возврат ↩️»;
- `cancel` — «Заказ отменён ❌»;
- `update` — «Заказ изменён менеджером ✏️»;
- `archive` — «Заказ архивирован 📦».

## Заключение

Order Center объединяет заказ как центральную бизнес-сущность платформы: клиент, состав услуг (брони), платежи, документы, партнёров, менеджеров и коммуникации в едином жизненном цикле. Раздел обеспечивает полный операционный контур — от создания заказа и подтверждения у поставщика до оплаты, документов, поездки и завершения, — с финансовым контролем (комиссия 12% / выплаты 88%), SLA (цель 48 ч), управлением возвратами и AI-поддержкой принятия решений. Тесная связка с Booking Center (состав заказа), Sales Center (выручка) и Analytics (KPI, география, активность) делает Order Center ядром операционного управления TravelHub.
