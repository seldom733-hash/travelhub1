# UI / UX аудит

Метод (обновлено 2026-10-25, завершающий проход): фактический браузерный прогон
Playwright (Chromium 1248, headless) на backend `:4000` + Next dev `:3000`.
30 состояний: `/`, `/search`, `/products/PRD-00018390`, `/login`,
`/app/finance/overview`, `/app/finance/obligations`,
`/app/finance/supplier-payments`, `/app/finance/reports/debt-as-of`,
`/app/finance/payment-terms`, `/app/payments`, `/app/requests` ×
1440/768/375 px + заполненные finance-состояния (обязательство с overdue,
PENDING-платёж, карточка платежа). Для каждого снимка собирались HTTP-статус,
console/page errors и горизонтальный overflow. Baseline и
`visual-report.json` — `docs/audit/ui-baseline/`.
Ограничение: одна тестовая учётная запись ADMIN; публичные сценарии
бронирования/оплаты не прокликивались (нет данных/внешних PSP);
storefront-страница не снята (нет ACTIVE витрины в dev-БД).

## 1. Дизайн-система

Что есть:
- Tailwind CSS 4 + `@theme` в `frontend/app/globals.css`: палитра
  (`brand`, `ink`, `panel`, `line`, `gold`, `dark`/`dark-surface`/`dark-border`),
  кастомные утилиты (`card-premium`, `destination-overlay`, `th-container`,
  `text-gold-gradient`, `fade-in-up`), темизация через `--th-*` переменные
  (font/bg/surface/border/text) — витрины партнёров могут переопределять тему.
- Иконки — единый набор `@phosphor-icons/react`.
- Локализация — `lib/i18n.tsx` (RU/AZ/EN, 3200+ строк), `formatPrice`,
  `formatDate`, `formatNumber` (Intl), переключение языка + `<html lang>`.

Чего нет:
- Каталога общих UI-примитивов (`components/ui` отсутствует): кнопки, поля,
  бейджи, модалки, таблицы определяются локально в каждом домене. Следствие —
  вариации отступов/радиусов/цветов между `components/public`,
  `components/internal`, `components/command-center`, `components/partner`.
- Общего `ErrorState`/`EmptyState`: каждый экран рисует своё (или молчит).
- ESLint-конфига, который ловил бы нарушения единообразия (см. REMAINING_WORK).

Оценка: визуальный язык узнаваем (тёмная витрина + золотой акцент, светлые
админ-таблицы), но системность поддерживается дисциплиной, а не примитивами.

## 2. Публичный сайт

Маршруты: `/`, `/search`, `/products/[slug]`, `/hotels`, `/catalog`,
`/categories`, `/store/[slug]`, `/orders`, `/bookings`, `/account/*`,
`/login`, `/register`, `/become-a-partner`, `/users`.

Сильные стороны:
- Единые карточки товаров (`components/public/ProductCard`, `Price`),
  skeleton-состояния (`components/public/Skeletons`), пагинация с aria-label,
  галерея media, фильтры категорий.
- PDP: цена/тарифы, календарь, медиа, продавец; загрузка — `loading.tsx`.
- Саджест и каталог — только публичный контур, без внутренних полей.

Исправлено в этом проходе:
- **Формат цен**: шесть секций главной показывали `350 USD` вместо
  локализованного `от 350,00 $` — теперь везде `formatPrice`.
- **Каноническое имя отеля**: один физический отель у разных поставщиков
  показывается одинаково в карточках, PDP и саджесте.
- **Глобальная ошибка**: `app/error.tsx` — вместо дефолтной страницы Next
  локализованное сообщение и кнопка «Повторить» без потери состояния.

Наблюдения (не менялись):
- Секции главной при ошибке запроса молча скрываются (`return null`) — нет
  retry/уведомления; для маркетингового блока это допустимо, но ошибку не
  видно в мониторинге.
- `app/layout.tsx` жёстко рендерит `<html lang="az">`; `LocaleProvider`
  обновляет `lang` после mount. SSR-разметка для сохранённой RU/EN-локали
  кратко неверна (a11y/SEO-нюанс).
- `globals.css` задаёт `color-scheme: dark` глобально, при этом админ-страницы
  и часть публичных карточек — светлые; нативные контролы (select/scrollbar)
  могут выглядеть тёмными на светлых экранах.
- Мобильная адаптивность реализована классами (`sm/lg/xl`), отдельного
  визуального прогона по breakpoints не было.

## 3. Административная панель

23 раздела `/app/*` (dashboard, command-center, requests, orders, bookings,
payments, finance, crm, partners, catalog, pricing, marketing, support,
documents, whatsapp, users, geography, hotel-directory, page-builder,
seller-profiles, settings, analytics, help).

Сильные стороны:
- 37 `loading.tsx` — у большинства разделов есть скелетоны.
- Командный центр: KPI-карточки с drilldown, очередь решений, кастомные панели.
- Таблицы реестров (requests/orders/bookings/payments) вынесены в компоненты,
  имеют пустые состояния и локализованные статусы.
- Доступ к действиям — по granular permissions; UI скрывает недоступные
  действия (проверяется компонентными тестами payments/requests).

Исправлено косвенно:
- Синхронизации поставщиков были недоступны из-за undeclared-прав — теперь
  ADMIN/DIRECTOR/OPERATOR получают корректные гранты (read), manage — ADMIN.
- Консольный `console.warn` в supplier controller заменён на Nest Logger —
  логи синков структурированы.

Наблюдения:
- Обратная связь после долгих операций (синк, merge отелей) — только
  лог/итоговый JSON; нет прогресса/тоста в UI (эндпоинты синков не имеют
  фронтового экрана).
- Часть админ-форм — крупные компоненты (PriceCalendarEditor 1210 строк,
  TourConstructor 1126, CRM page 893) — кандидаты на декомпозицию.
- `help-registry` и `help-i18n` — статические словари на 1385/801 строк,
  дублируют часть текстов i18n.

## 4. Состояния и доступность

- Загрузка: скелетоны на публичном PDP и админ-разделах; у публичного поиска
  skeleton'ы в секциях главной.
- Пусто: локализованные пустые состояния в таблицах/витрине, часть секций
  скрывается.
- Ошибка: единый error boundary (добавлен), API-ошибки в формах показываются
  текстом; в календаре — распознавание 429/503 и retry.
- Доступность: aria-label у пагинации/навигации, роли dialog в help-попаверах,
  focus-visible стили у части кнопок; централизованного a11y-аудита нет.

## 5. Результаты браузерного прогона (2026-10-25)

Автоматические метрики: 30/30 состояний открылись без HTTP-ошибок, без
console/page errors и без горизонтального overflow на 1440/768/375 (после
исправлений). Ручной просмотр скриншотов выявил и исправил:

| Находка | Где | Серьёзность | Исправление |
|---|---|---|---|
| Значения таблиц/панелей finance почти невидимы: светлый `#e8e8e8` текст на белом (наследие тёмной витрины) | admin `<main>`, PanelFrame | P1 (нечитаемые суммы) | светлая база контура (`text-slate-900`, `bg-slate-50`), явный цвет в панели |
| На 375 px sidebar 240 px выталкивал заголовок/карточки/таблицу за экран | `Shell.tsx` | P1 (мобильный admin) | авто-collapse <768px + resize, rail 72 px |
| Нативные checkbox/date в светлом admin — чёрные | `Shell.tsx` | P3 | `color-scheme: light` на admin main |
| Дата платежа — сырой ISO вместо локали | supplier payments table | P3 | `formatDate` |
| Поля распределения обрезают placeholder в узкой панели | payment detail | P3 | одноколоночная сетка |
| PDP на 375 px: шапка публичного layout выходит за экран (Register/внутренние ссылки) | `PublicLayout.tsx` | P1 (мобильный public) | вторичные ссылки (Register/Аккаунт/Выход) скрыты `<sm`, остаётся основное действие |
| KPI панели показывают `0.00 ₼` для пустых значений | overview/payments | P3 | оставлено: 0 — валидное денежное значение, формат единый |

Визуально подтверждено: публичная главная (тёмная тема, hero, поиск) выглядит
целостно; finance-реестры читаемы после фикса; overdue-строка и KPI
подсвечиваются; карточка платежа показывает allocated/unallocated и действия
confirm/cancel.

Остаточные UX-дефекты: таблица платежей на 375 px скроллится горизонтально
внутри контейнера (стандартный паттерн, но можно перейти на карточки); AZ-дата
`2026 M10 25` необычна — решить продуктово (ISO vs locale); деталь/форма
открывается inline-панелью слева, а не правым drawer'ом (существующий
PanelFrame-паттерн).

## 6. Приоритетные UX-задачи (осталось)

1. Вынести `components/ui` (Button/Input/Select/Badge/Modal/Table/State) и
   перевести на них хотя бы новые экраны — снимет вариативность.
2. Консолидировать 6 marketplace-секций в один компонент с вариантами
   (`card`/`skeleton`/`section`).
3. Показывать прогресс и результат фоновых операций (синк, merge, экспорт) в
   интерфейсе, а не только в ответе API.
4. Локализовать `<html lang>` на SSR (cookie/заголовок Accept-Language) и
   привести `color-scheme` к теме конкретного layout.
5. Провести визуальный screenshot-прогон ключевых страниц (375/768/1440) после
   подключения dev-серверов — зафиксировать baseline в `docs/audit/ui/*`.
