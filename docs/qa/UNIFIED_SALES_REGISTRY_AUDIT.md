# Единый реестр вместо разделов «Заявки / Заказы / Брони» — аудит предложения

Дата: 04.11.2026

## 1. Предложение

Убрать из левого меню три пункта:

```text
Заявки
Заказы
Брони
```

Оставить один раздел:

```text
Финансы → Реестр продаж и взаиморасчётов
```

В карточке реестра добавить блок туристов, который заполняется:

- при создании новой заявки;
- после принятия клиентом.

## 2. Главный вывод

Идея правильная как **единая операционная точка входа**, но в текущем виде её нельзя реализовать простым удалением трёх пунктов меню. Реестр сейчас является финансовым отчётом, а не полноценной заменой трём операционным разделам.

Нужна поэтапная миграция.

## 3. Ограничения

### 3.1. Права доступа

Реестр требует:

```text
finance.overview.read
```

У `SALES_MANAGER` и `OPERATOR` этого права нет. Если убрать «Заявки», «Заказы», «Брони», менеджеры и операторы потеряют доступ к своей работе.

Варианты:

1. Выдать `finance.overview.read` менеджерам и операторам — они увидят все финансовые KPI компании.
2. Ввести отдельное право `sales.registry.read` и отдельную проекцию реестра без финансовых сумм.
3. Сделать реестр роль-зависимым: менеджер видит только свои сделки, оператор — только операционные поля.

Рекомендую вариант 2/3: единый реестр, но с разными полями и scope по роли.

### 3.2. Реестр не покрывает все заказы

`DealsService.loadRows()` начинает выборку с заявок:

```ts
const requests = await prisma.request.findMany({ ... take: 1000 });
const orders = await prisma.order.findMany({
  where: { OR: [{ id: { in: orderIds } }, { commerceSequence: { in: sequences } }] }
});
```

Следствия:

- заказ без связанной заявки не попадёт в реестр;
- заявки старше лимита 1000 не попадут;
- заказ, созданный напрямую через checkout/order path, может отсутствовать.

Перед удалением разделов «Заказы» нужно убедиться, что все заказы имеют заявку или изменить источник реестра на `Order` + `Request`.

### 3.3. Одна сделка — несколько броней

Сейчас:

```ts
const bookingByOrder = new Map(bookings.map((b) => [b.orderId, b]));
```

На один заказ берётся только одна бронь, последняя в выборке. При частичном исполнении или нескольких услугах:

- в реестре будет только одна бронь;
- остальные брони не видны;
- действия по ним недоступны.

Раздел «Брони» нельзя убирать, пока реестр не поддерживает:

```text
bookings: BookingSummary[]
```

и выбор конкретной брони в карточке.

### 3.4. В карточке нет полного набора действий брони

Карточка сделки сейчас умеет:

- действия заказа;
- платежи;
- график;
- документы;
- коммуникации;
- заметки.

Она не умеет:

- `prepare/send/requestClarification/confirm/reject/service/complete` брони;
- `requestChange/resolveChange`;
- `requestCancellation/cancel`;
- `returnToOrder`.

Если убрать «Брони», эти операции станут недоступны.

### 3.5. Уведомления и deep links

Счётчик заявок в `Shell.tsx` привязан к:

```text
/app/requests
```

Уведомление ведёт на:

```text
/app/requests/<id>
```

Если убрать пункт «Заявки», нужно:

- оставить маршруты `/app/requests/*`;
- перенаправить badge на реестр с фильтром «мои новые»;
- обновить mark-as-read при открытии сделки в реестре.

Удалять сами страницы нельзя — на них ведут ссылки из карточек, писем и уведомлений.

### 3.6. Туристы: два разных жизненных цикла

#### Заявка

Модель:

```text
RequestTraveler
  firstName
  lastName
  birthDate (обязательно)
```

API:

```text
GET    /requests/:id/travelers
POST   /requests/:id/travelers
PATCH  /requests/:id/travelers/:travelerId
DELETE /requests/:id/travelers/:travelerId
```

Право:

```text
order.edit_noncritical
```

Ограничения:

- редактирование запрещено после `CONVERTED`;
- запрещено в `REJECTED`;
- количество строк не может превышать `travelerCount`;
- `customerAccept` требует **полный состав** уже на стадии заявки.

#### Заказ

Модель:

```text
OrderTraveler
  firstName
  lastName
  birthDate
  citizenship
  gender
  passportSeries
  passportNumber
  passportExpiry
  dataCompleteness
```

API:

```text
GET   /orders/:id/travelers
PATCH /orders/:id/travelers
PATCH /orders/:id/travelers/:travelerId
POST  /orders/:id/validate-completion
POST  /orders/:id/final-confirm
```

Требования:

- для `COMPLETE` нужны паспортные данные;
- `confirm` заказа требует всех туристов `COMPLETE`;
- `final-confirm` фиксирует состав перед бронированием.

## 4. Конфликт с «заполнением после принятия клиентом»

Сейчас клиент **не может принять заявку**, пока не заполнены все туристы:

```ts
await this.assertTravelersReadyForCommercialStep(request);
```

Это происходит в `customerAccept`.

То есть текущая последовательность:

```text
NEW → CHECKING → CONFIRMED/PRICE_CHANGED
→ заполнить всех RequestTraveler
→ CUSTOMER_ACCEPTED
→ CONVERTED
```

Если бизнес хочет:

```text
CUSTOMER_ACCEPTED → заполнить туристов → CONVERTED
```

то нужно менять D3-инвариант:

- убрать проверку из `customerAccept`;
- перенести её в `convertRequestToOrder`;
- разрешить `CUSTOMER_ACCEPTED` с неполным составом;
- проверить, что все текущие тесты и сценарии не рассчитывают на ранний gate.

Это не косметическое изменение. Оно влияет на:

- фиксацию требований к туристам;
- конверсию в заказ;
- расчёт `travelerCount`;
- бронирование;
- аудит.

## 5. Что нужно сделать до удаления пунктов меню

### Обязательно

1. Добавить в реестр блок туристов:
   - на стадии заявки — `RequestTraveler`;
   - на стадии заказа — `OrderTraveler`;
   - с разными полями и правами.
2. Добавить в карточку действия брони.
3. Поддержать несколько броней на заказ.
4. Проверить, что реестр показывает все заказы, включая заказы без заявки.
5. Дать менеджерам/операторам доступ к реестру без раскрытия всех финансов.
6. Перенаправить уведомления и badge на реестр.
7. Оставить маршруты `/app/requests/*`, `/app/orders/*`, `/app/bookings/*` для deep links.

### Рекомендуемая последовательность

#### Этап 1. Единая точка входа

- оставить все три раздела в меню;
- добавить в реестр вкладку «Туристы»;
- добавить кнопки «Заявка / Заказ / Бронь» из карточки.

#### Этап 2. Реестр как рабочее место

- добавить действия брони;
- поддержать несколько броней;
- добавить роль-зависимый scope;
- перенести badge уведомлений.

#### Этап 3. Скрытие меню

- скрыть три пункта;
- оставить прямые маршруты;
- добавить в реестр фильтры «Мои заявки», «Мои брони», «Требуют внимания».

## 6. Предлагаемая структура карточки

```text
Сделка
├── Обзор
├── Туристы
│   ├── Заявка: ФИО + дата рождения
│   └── Заказ: паспорт + complete/final-confirm
├── Услуги
├── Платежи клиента
├── Расчёты с поставщиком
├── Бронь
│   ├── действия
│   └── документы
├── Документы
├── Коммуникации
└── История
```

## 7. Вывод

Убирать пункты меню сейчас нельзя без потери операционных возможностей.

Правильный порядок:

1. Сначала сделать реестр полноценной карточкой сделки.
2. Потом скрыть дублирующие разделы.
3. Routes оставить навсегда как deep links.

Отдельно нужно решение по туристам: оставлять текущий gate «туристы до принятия клиентом» или переносить заполнение после принятия. Это изменение D3-модели, а не просто UI.
