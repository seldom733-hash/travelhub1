# ETG / RateHawk — Implementation Roadmap

Только план будущей разработки. Реализация на данном этапе не выполняется.

## Этап 1. Устранение блокирующих архитектурных пробелов

**Цель:** подготовить инфраструктуру для supplier booking.

- Добавить `EtgAdapter implements SupplierAdapter` + регистрация в `supplier.module.ts`.
- Вынести supplier booking contract: `book`, `prebook`, `recheck`, `cancel`, `status`.
- Добавить внешние ID (HCN) в `SupplierConfirmation` и использовать их.
- Ввести idempotency-ключи для booking-операций.

**Зависимости:** документация ETG (endpoints, контракты).
**Критерии готовности:** адаптер зарегистрирован, unit-тесты проходят, tsc чистый.
**Тесты:** unit (adapter), integration (HTTP mock).

## Этап 2. Адаптер и контракты ETG

**Цель:** реализовать HTTP-клиент ETG с auth, retry, circuit breaker, тайм-аутами.

- Auth (API key / token) через env/секреты.
- Retry с backoff, circuit breaker (resilience модуль).
- Логирование без секретов и PII.

**Зависимости:** Этап 1, документация ETG.
**Критерии готовности:** HTTP-вызовы работают в sandbox, логи без секретов.
**Тесты:** unit (HTTP mock), integration.

## Этап 3. Поиск и mapping отелей

**Цель:** поиск отелей ETG → канонический каталог TravelHUB.

- Поиск по направлению/стране/городу/отелю/списку IDs.
- Chunking списков hotel IDs.
- Mapping: `HotelSupplierRef` (supplierCode=ETG, externalKey=ETG hotel id).
- Cross-supplier merge по (normalizedName, countryCode, cityName) с единственным кандидатом.

**Зависимости:** Этап 2, geo-ingest.
**Критерии готовности:** поиск возвращает offers, mapping создаёт refs.
**Тесты:** unit + integration.

## Этап 4. Цены и повторная проверка

**Цель:** актуальная цена и доступность перед бронью.

- Recheck/Prebook endpoint и TTL предложения.
- Модель налогов/сборов (включённые/дополнительные).
- FX + markup + налоги → public price.
- Допустимое изменение цены: пороги, согласие клиента.

**Зависимости:** Этап 3, документация ETG (Prebook TTL, налоги, пороги).
**Критерии готовности:** recheck возвращает актуальную цену, изменение цены обрабатывается.
**Тесты:** unit + integration + негативные.

## Этап 5. Бронирование и подтверждение

**Цель:** создание брони у ETG и сохранение подтверждения.

- Book endpoint → внешний ID (HCN) → `SupplierConfirmation.confirmationNumber`.
- Idempotency: повторный запрос не создаёт дубль.
- Тайм-аут: определение фактического состояния.
- Обновление внутреннего Booking/Order.

**Зависимости:** Этап 4, документация ETG (HCN-поле, idempotency).
**Критерии готовности:** бронь создаётся, HCN сохраняется, статус синхронизирован.
**Тесты:** unit + integration + конкурентные.

## Этап 6. Отмена и восстановление после ошибок

**Цель:** отмена брони у поставщика + компенсация.

- Cancel endpoint → результат → обновление статуса.
- Обработка отказа/тайм-аута поставщика.
- Восстановление после перезапуска.

**Зависимости:** Этап 5.
**Критерии готовности:** отмена вызывает реальную отмену у поставщика.
**Тесты:** unit + integration + негативные.

## Этап 7. Многокомнатные заказы

**Цель:** поддержка нескольких комнат разных типов в одном заказе.

- Multi-room DTO/UI/backend.
- Per-room конфигурация (тип, тариф, питание, гости, цена).
- Подтверждение части конфигурации поставщиком.

**Зависимости:** Этап 5.
**Критерии готовности:** заказ с N комнатами разных типов бронируется и подтверждается.
**Тесты:** unit + integration + e2e.

## Этап 8. Безопасность, наблюдаемость и тесты

**Цель:** production-ready качество.

- Секреты в env/секрет-менеджере, не в логах.
- PII-редактирование в логах (уже есть `pii.spec.ts`).
- Тайм-ауты, retry, circuit breaker.
- Гонки состояний, транзакционные границы.
- Unit/integration/e2e тесты для всех критических сценариев.

**Зависимости:** Этапы 1–7.
**Критерии готовности:** все тесты проходят, нет утечек секретов/PII.
**Тесты:** полный набор.

## Этап 9. Квалификация перед production

**Цель:** финальная проверка.

- Sandbox-тесты с реальным ETG (read-only + тестовые брони).
- Проверка цен, налогов, статусов, отмен.
- Нагрузочное тестирование.
- Sign-off владельца проекта.

**Зависимости:** Этап 8.
**Критерии готовности:** все сценарии A–F проходят, sign-off получен.

## Условия PASS для каждого этапа

- Код компилируется (tsc --noEmit).
- Тесты проходят (unit + integration).
- Нет утечек секретов/PII в логах.
- Документация обновлена.
- Владелец проекта подтвердил переход к следующему этапу.
