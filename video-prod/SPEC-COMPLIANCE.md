# Соответствие ТЗ на два обучающих видео — фактическая проверка

Дата проверки: 12.11.2026. Стенд: frontend `:3000`, backend `:4000`, Postgres `:5432`.
Проверка выполнена на реальном интерфейсе (Playwright) и запросами к БД.

## Подтверждено (можно показывать)

| Требование ТЗ | Факт | Доказательство |
|---|---|---|
| Единый раздел «Реестр продаж», без отдельных «Заявки/Заказы/Брони» | да | меню рабочего пространства: только «Реестр продаж и взаиморасчётов» |
| Три категории универсального поиска | да | вкладки «Туры», «Отели», «Авиабилеты» на `/search` |
| Фильтр багажа | да | «Тариф (багаж)»: BUDGET / CLASSIC / PLUS / COMFORT / BUSINESS |
| «Туда-обратно» | да | переключатель на вкладке авиабилетов |
| Прямой рейс | да | переключатель на вкладке авиабилетов |
| Витрина: только туры и отели, без авиабилетов | да | `/catalog`, поиск в шапке — туры/отели |
| Карточка: календарь месяца, состав туристов, цены на датах, варианты размещения | да | `/products/:code` |
| Гость: кнопка заявки неактивна до заполнения данных | да | `disabled=true` до ввода имени/фамилии/телефона/почты |
| Авторизованный: заявка без повторного ввода данных | да | заявки `REQ-00000007`, `REQ-00000008` |
| Четыре демо-заявки | да | `REQ-00000005…08`: гость/аккаунт × витрина/поиск |
| Автоматическое распределение заявок | да | `SalesAssignmentSettings.mode = AUTO`; профили менеджеров с `participatesInAutoDistribution` |
| Фактический назначенный менеджер | да | `lastAssignedAt` совпадает с созданием заявок: Elvira — `REQ-00000007`, Natalya — `REQ-00000008` |
| Трекинг обработки | да | поля `assignedAt`, `firstOpenedAt`, `processingStartedAt`, `firstContactAt`, `slaDueAt`, `assignmentState` |
| Request → Order → Booking | да | сделка `00000008`: заявка → заказ `ORD-00000003` → бронь → исполнение |
| Платёж клиента с подтверждением | да | `PAY-00000001`, статус `PENDING` → кнопка «Подтвердить» → оплата заказа `PAID` |
| Смена цены и согласие клиента | да | сделка `00000007` → состояние «цена изменилась», действия «Клиент принял / отказался» |
| Финансовое завершение ≠ закрытие | да | после завершения брони кнопки закрытия нет, пока не прошла дата услуги |

## Не подтверждено (требуется уточнение, не имитировать)

| Требование ТЗ | Факт | Что найдено |
|---|---|---|
| Указание **возраста каждого ребёнка** в поиске | **да** | поле возраста появляется, когда количество детей больше нуля; для младенцев — аналогично |
| Перерасчёт стоимости при расхождении возраста ребёнка с паспортом | **не подтверждено** | механики автоматического перерасчёта по возрастной категории на дату услуги не найдено |
| Реальное **персональное уведомление** менеджера о новой заявке | **нет** | у менеджера `Natalya` не найдено на `/app/dashboard`, `/app/finance/deals`, `/app/my-status`; блок «оповещения» у администратора — общая лента событий реестра, не персональное уведомление |
| Прикрепление **подтверждающего документа** к платежу клиента | **нет** | в `finance.Payment` нет поля документа; в форме платежа только сумма, способ и причина. У платежей поставщику есть отдельная сущность `SupplierPaymentEvidence` |
| Возраст ребёнка на дату услуги (правило расчёта) | **нет** | концепции возрастной категории на дату в системе не найдено |

## Следствия для производства

1. Сцены про **автоматический перерасчёт при расхождении возраста** снимаются как неподтверждённые: логика перерасчёта по возрастной категории на дату услуги в интерфейсе не найдена. Само поле возраста ребёнка в поиске **есть** и показывается в ролике.
2. Сцену «менеджер получает реальное уведомление» **невозможно снять** — показывается только автоназначение (что реально есть) и экран-замечание об отсутствии персональных уведомлений.
3. «Прикрепить подтверждающий документ к платежу» — показывается фактическая форма (сумма, способ, причина) и замечание о недостающем поле.
4. Всё остальное из ТЗ снимается на реальном интерфейсе.
