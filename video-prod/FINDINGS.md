Дата: 2026-11-11. Стенд: frontend `:3000`, backend `:4000`, Postgres `:5432`.
Проверено вживую через браузер (Playwright) и запросами к API/БД.

- Рабочее пространство: 12 экранов (`/app/command-center`, `/app/requests`, `/app/orders`,

- Путь туриста: регистрация → карточка товара → заявка. Создана заявка `REQ-00000016`
  (2 461,79 AZN, 2 туриста).
- Путь сотрудника: «Взять себе» → «Начать обработку» → «Подтвердить цену» →
  «Клиент принял условия» → добавление туристов → «Создать заказ». Создан заказ
  `ORD-00000013` / `TH-2026-000013`, 2 записи `OrderTraveler`.

## Найденные дефекты (требуют исправления)

### 0. Бэкенд запущен из устаревшей сборки `dist`

Процесс: `node dist/main.js` (PID 13844), `dist/modules/order/order.service.js`
от 08.11.2026, а исходники новее. Из-за этого UI и API расходятся:

- `dist` `getOrderTravelers()` возвращает **массив**, текущий исходник — объект
  `{pinnedRequirements, travelerCount, travelers, …}`;
- `dist` `canViewTravelerPii()` пускает только `OPERATOR`/`ADMIN`, исходник —
  ещё и `SALES_MANAGER`/`SALES_HEAD`.

Исправление: `npm run build` + перезапуск бэкенда. После этого пункты 1–2 снимаются.

### 1. Блок «Данные туристов» в заказе падает на старом билде

`/app/orders/:id`, секция «ДАННЫЕ ТУРИСТОВ» → `t.travelers is not iterable`.

Причина — рассинхрон сборки: `GET /api/v1/orders/:id/travelers` отдавал массив,
а `frontend/components/order/TravelerCollectionPanel.tsx:92-96` ожидает объект
`{ travelers: [...], travelerCount }`. В актуальных исходниках бэкенд отдаёт
нужный объект, фронт ему соответствует.

Следствие на старом билде: нельзя ни увидеть, ни отредактировать данные туристов,
ни пройти гейт готовности к бронированию.

### 2. ~~Дата рождения теряется~~ — ПРОВЕРЕНО: НЕ ПОДТВЕРДИЛОСЬ (PII-редакция)

В БД `OrderTraveler.birthDate` заполнен (`1991-04-11`, `1988-09-02`) — данные
переносятся корректно. В API поле было `null`, потому что роль смотрит через
фильтр PII (`backend/src/shared/pii.ts`).

В текущих исходниках `canViewTravelerPii` разрешает `OPERATOR`, `ADMIN`,
`SALES_MANAGER`, `SALES_HEAD`. В запущенной старой сборке — только `OPERATOR`/`ADMIN`.
То есть на старом билде `Natalya` (SALES_MANAGER) не видит дату рождения и паспорт,
хотя по актуальной политике должна.

Вывод: дефект кода отсутствует, есть **устаревшая сборка** `dist` (см. №0).

### 3. На публичной карточке товара раскрыты служебные атрибуты поставщика

`/products/PRD-00021841`, блок «Характеристики»: `WWW`, `SLUG`, `MEAL INC`
(`-2147483647`), `ROOM INC`, `CAT CLAIM` (hex-дамп), `TOUR INC` и т.п.

Следствие: турист видит внутренние коды интеграции; выглядит как утечка
и подрывает доверие к карточке.

### 4. Кнопка с сырым ключом вместо названия

Карточка заказа: кнопка называется `requestCancellation` вместо русского текста
(пропущен ключ i18n).

### 5. «Взять себе» остаётся активной после назначения

После нажатия кнопка не исчезает и не блокируется, статус назначения не виден.
Риск повторных действий и непонимания, кто ответственный.

### 6. Партнёрская витрина не демонстрируема: в системе нет ни одной витрины

`catalog.PartnerStorefront = 0`, `sales.Sale = 0`, `sales.Quote = 0`,
`sales.CheckoutIntent = 0`. Партнёрские учётки неактивны (`demo.partner` — INACTIVE).

Следствие: сценарий «покупка с витрины → сделка» в текущем виде не показать.
Работает только покупка из маркетплейса (гостевая/клиентская заявка) с последующей
конверсией в заказ. Нужно либо активировать партнёра и витрину, либо назвать это
в ролике как незакрытый участок.

### 7. Карточка заявки не открывается по коду

`/app/requests/REQ-00000016` — пустая страница; `/app/requests/<uuid>` — работает.
Плохо для поддержки и для ссылок в инструкции.

### 8. Нет данных для показа платежей и броней

`finance.Payment = 0`, `booking.Booking = 0`. Чтобы показать оплату и бронирование,
их нужно создавать в кадре (это же и есть содержание инструкции).

## Что это значит для видео

- Ролик 1 (турист): снимается почти без ограничений, кроме дефекта №3
  (служебные атрибуты в карточке).
- Ролик 2 (сотрудники): до исправления №1 и №2 полный цикл
  «заявка → заказ → данные туристов → бронь → оплата → завершение» показать нельзя —
  обрывается на данных туристов.

## Итог проверки (после пересборки и прогона)

Исправлено по ходу:
- маршрут `GET /api/v1/orders/:id/travelers` теперь отдаёт полный объект
  (`getPinnedRequirements`), панель данных туристов работает;
- бэкенд пересобран (`npx tsc -p tsconfig.build.json --incremental false`) и
  перезапущен — PII-политика и контракт туристов совпали с исходниками.

Подтверждены живьём:
- Полный цикл в реестре продаж: сделка `00000016` — заявка → заказ → бронь
  `BKG-00000024` → данные туристов (`COMPLETE`) → платёж `PAY-00000004` (`CAPTURED`,
  наличные, 2 461,79 AZN) → бронь `COMPLETED` → заказ `FULFILLED`.

Остаются к исправлению:
1. Технические подписи кнопок: `requestCancellation`, `waitFirstPayment`.
2. Код метода в списке платежей отображается как `cash` вместо «Наличные».
3. После финального подтверждения карточка не обновляется без перезагрузки.
4. В карточке заказа кнопка «Платёж клиента» исчезает после создания брони
   (`!order.linkedBooking` в `orders/[id]/page.tsx:381`) — оплата возможна только
   до брони или из карточки сделки.
5. Наценка не применилась: сумма продажи = себестоимость (2 461,79), доход 0.
   Проверить правила в «Наценки и комиссии» и привязку к поставщику.
6. Партнёрских витрин нет (`PartnerStorefront = 0`) — покупку с витрины не показать.
7. Служебные атрибуты поставщика в публичной карточке услуги (дефект №3).
